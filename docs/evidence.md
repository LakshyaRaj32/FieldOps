# Evidence (photos)

> Status: **implemented in Phase 4 (Field Operations)**; not yet verified on a device (see
> [phase-status.md](phase-status.md#phase-4--field-operations)).

The assigned worker attaches photos to a job, online or offline. This first implementation
supports **photos (JPEG, PNG)** only. Documents and signatures are later work: they reuse the
same pipeline with other validators.

## Ownership of the data

| What | Where |
| --- | --- |
| Photo bytes, before upload | App-private files, `files/evidence/<evidenceId>.jpg` on the phone |
| Pending upload (the command) | SQLite outbox entry `job.evidence.add` (Phase 3 outbox) |
| Which local files exist | SQLite `evidence_files` (for cleanup) |
| Photo bytes, after upload | Object storage (`ObjectStorage`): a private Cloudflare R2 bucket when deployed, local disk in development |
| Metadata | PostgreSQL `job_evidence` |

Binary data never goes into SQLite or PostgreSQL.

## Upload flow

```text
Take photo / Choose photo            react-native-image-picker (resized to ≤1920 px, JPEG q0.8)
   ▼
Type check (JPEG/PNG), size ≤10 MB   on the phone: no doomed upload waits in the outbox
   ▼
Copy to files/evidence/<id>.jpg      FieldOpsFiles Kotlin module (the picker's cache may be cleared)
   ▼
LocalJobStore.addEvidence            ONE SQLite transaction: outbox row + evidence_files row
   │                                 + local view (the photo appears at once, "Waiting to upload")
   ▼
JobSyncEngine (Phase 3 rules)        FIFO per job, backoff, dead letter, Idempotency-Key
   │  POST /jobs/:id/evidence  multipart: id, capturedAt, file      (120 s timeout)
   ▼
Server                                auth → policy (assigned worker) → evidence ID replay check
   │                                 → size → inspectImage (bytes) → strip metadata
   │                                 → ObjectStorage.put → INSERT job_evidence + processed_mutations
   ▼
Response: the job with its evidence  → server copy in SQLite → "Uploaded"
```

States shown on each photo: **Waiting to upload** (pending), **Uploading…** (in flight),
**Uploaded**, **Upload failed** (the worker sees the reason in the job's problem list and can
dismiss it or retry).

### Why the outbox and not a separate upload queue

A photo is a command like any other ("attach this evidence to this job"), so it gets the
outbox's guarantees for free: durable across restarts, one attempt at a time per job in
order, exponential backoff, offline attempts not counted, dead letter after 10 server
failures, visible problems, and exactly-once effect through `Idempotency-Key` plus the
device-generated evidence ID. The only specialized parts are at the edges: the file lives on
disk (the payload holds its URI), the transport sends multipart, and the upload has a longer
timeout.

**Boundary.** The whole photo is sent in one request. For FieldOps-sized photos (≤1920 px,
typically 200 KB–1 MB) that is fine; resumable or chunked uploads, and presigned direct
uploads to S3, become worthwhile with large files or video (not planned).

## Server

`apps/api/src/jobs` (evidence is a child collection of a job, like notes):

- `POST /api/v1/jobs/:id/evidence` (assigned WORKER) — multipart, `file` + `id` + `capturedAt`.
- `GET /api/v1/jobs/:id/evidence/:evidenceId/content` (anyone who may see the job) — the
  bytes, `Cache-Control: private`, `X-Content-Type-Options: nosniff` (helmet).
- `JobDetail.evidence` lists metadata (also in the worker's working set).

### Storage

`src/storage/` holds the `ObjectStorage` interface (`put`, `get`, `delete`) with two
implementations, chosen by `STORAGE_DRIVER`:

| Driver | Class | Used in |
| --- | --- | --- |
| `local` (default) | `LocalDiskObjectStorage` under `STORAGE_DIR` (default `apps/api/storage`, gitignored). Writes go to a temporary file and are renamed into place | Development, and any host with a persistent disk |
| `s3` | `S3ObjectStorage` (AWS SDK v3, the client Cloudflare documents for R2) | **Render: Cloudflare R2**, whose free plan has 10 GB and no download fees. Locally: the S3Mock compose service |

What both have in common:

- **The database stores the key, never a URL.** Keys are generated by the server
  (`evidence/<jobId>/<evidenceId>.jpg`) and validated against a strict pattern before any
  disk or bucket call.
- **The bucket is private.** Every download goes through
  `GET /jobs/:id/evidence/:evidenceId/content`, which checks that the caller may see the job
  (organization, role, team or shop) before reading the object. A public link would bypass
  those checks.
- **Callers don't know which driver is in use.** Moving to another S3-compatible provider is a
  configuration change.

Configuration for R2: `STORAGE_DRIVER=s3`, `S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com`,
`S3_REGION=auto`, `S3_BUCKET`, and an R2 API token's `S3_ACCESS_KEY_ID` and
`S3_SECRET_ACCESS_KEY` (Object Read & Write on that bucket only). Invalid or missing values stop
the process at startup, and secrets never appear in the error. An unreachable bucket is logged
at startup but does not stop the API.

**Why not local disk on Render:** the free plan's disk is wiped on every deploy, restart and
wake-up from sleep. Rows in PostgreSQL (Supabase) survive, but their files don't, so every
photo would break after the next deploy.

**Possible later step:** signed links (the API checks access, then redirects to a temporary R2
URL) would save the API's bandwidth. Same keys, same permission checks. No CDN.

## Validation

| Check | Rule | Error |
| --- | --- | --- |
| Permission | `job:evidence` (WORKER), assigned to the job | 403 / 404 |
| Size | ≤ 10 MB (multer limit and service check) | 413 `PAYLOAD_TOO_LARGE` |
| Type | Detected from the **bytes** (JPEG `FF D8`, PNG signature); the client's MIME type and file name are ignored and never stored | 415 `UNSUPPORTED_FILE_TYPE` |
| Structure | JPEG marker segments / PNG chunks must be complete; a frame header must give the size | 415 |
| Dimensions | 1–10 000 px per side, ≤ 40 megapixels | 415 |
| Per job | ≤ 50 photos | 422 `EVIDENCE_LIMIT_REACHED` |
| ID | Device UUID; the same ID again = replay; an ID belonging to other evidence | 422 `IDEMPOTENCY_KEY_REUSED` |
| Capture time | ISO 8601 with a time zone (device time, informational) | 400 |

Executables, HTML, SVG, PDF, GIF and HEIC are all refused (the app refuses non-JPEG/PNG
before upload too). File names are never used: the stored name is the evidence ID.

### Metadata removal

`src/jobs/domain/evidence-image.ts` (pure, byte-level, unit-tested) copies the file without
its metadata: JPEG APP1–APP15 segments (EXIF with GPS, XMP, IPTC) and comments; PNG `eXIf`,
text and time chunks, and anything after `IEND`. Pixel data is copied untouched (no decode or
re-encode). The one value kept is the EXIF **orientation**, rewritten as a minimal EXIF block,
because camera photos are often stored sideways. The SHA-256 of the stored bytes is recorded.
The same photo attached twice to one operation (the same bytes after processing) is stored
once: the second upload succeeds and returns the operation unchanged, so an offline retry
never fails.

## On the device

`FieldOpsFiles` Kotlin module (`importFile`, `fileExists`, `deleteFile`), confined to
`files/evidence` (names validated, deletes outside refused). A photo file is deleted when
nothing needs it any more: its upload was dismissed, or it was uploaded and either the synced
entry was pruned (7 days) or the job left the phone. Until then the gallery shows the local
copy (works offline); otherwise the server copy is loaded with the access token.

If a pending photo's file disappears (storage cleared by the user), the upload fails for good
with "The photo is no longer on this phone" instead of retrying forever.

## Known limits

- A crash between writing the object and recording its metadata leaves an orphan object;
  a cleanup job belongs with Phase 5 workers.
- No thumbnails: the gallery loads the (resized) photo itself.
- Images are cached per the platform image cache for the session; the access token in the
  request header is read at render time.
